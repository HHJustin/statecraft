## 三、真机暴露的问题（按严重度）

### P0-1：模型报完问题没写终止标记 → 整个任务 Blocked，产出全废

**现象**：审 `click/parser.py`（428 行），模型报了 15 条以上，最终状态 `Blocked`，原因"执行产出缺少 DONE 标记"。已记录的 15 条全部不作数。

**根因两层**：

1. `Agent.max_tool_iters = 4`。审查是"每条问题一次 `record_finding`"的活，428 行文件 4 轮工具对话装不下。轮次一耗尽，`run()` 直接返回"（达到工具循环上限，未给出最终输出）"——**连输出总结的机会都没有**。
2. 编排器 `_advance` 用"输出里有没有 `REQUEST_REVIEW`/`DONE`"判断执行是否完成。少一个字符串 = 判定失败 → 重跑（**每次重跑都从头 read_file + 重报，白花钱**）→ 超限 Blocked。

**修法**（两处互补，都在内核，共 ~15 行）：

```python
# ① runner.py：轮次耗尽 ≠ 任务失败，补一次「不许调工具、只输出结论」的收尾轮
messages.append({"role": "user", "content":
    "工具调用次数已达本轮上限。现在**不要再调用任何工具**，"
    "直接输出最终结论（必须包含此前约定的终止标记）。"})
reply = await self.llm.chat(messages, tools=None)

# ② orchestrator.py：少一个标记不算失败，要看有没有实质产出
elif getattr(agent, "mutations", 0) > 0:
    transition(task, "Reviewing", reason="no_marker_but_mutated")
```

配套：`Tool` 新增 `mutates: bool` 字段（`record_finding` / `declare_clean` 标 True），`call_tool` 执行成功后累加 `agent.mutations`。这是"确实干了活"的**确定性证据**，不依赖模型措辞——和之前"Reviewing 去向不能看 DONE"是同一类修法。

审查示例同时把 `max_tool_iters` 提到 10。

**验证**：同一份 428 行代码，复跑 `Done`，4 条有效发现进报告。

> 附带发现：第一次那"15 条"其实是 Blocked 后 3 次重跑**累积**出来的假数字（session 跨重试不清空）。也就是说，**Blocked 不只是丢产出，还会污染统计**。

### P0-2：一条都没报 → 审核者也盖章通过（双盲通过）

**现象**：审 `flask_sessions.py`（388 行）+ `requests_hooks.py`，结果 `0 条有效`、`0 驳回`、`Done`。而单独审 `requests_hooks.py` 能报 4 条。388 行的 Flask 代码不可能没问题。

**根因**：这是审查系统最危险的失效模式——**漏报**。

- reviewer 的 prompt 写着"没有缺陷就一条都不报，凑数编造会被驳回"，把"防幻觉"做成了"防报告"；
- critic 只审"已有 finding 是否成立"，**没有审"应该有的 finding 在不在"**；
- 系统没有"零产出"的概念：`0 条 + 审核通过 = 成功`。

**修法：内核加一个应用可注册的「完成条件」扩展点**（内核 ~12 行，业务语义全在应用层）：

```python
# orchestrator
completion_check: Callable[[Task], str | None] | None = None
# 返回 None = 达标；返回字符串 = 还缺什么（注入下一轮上下文 + 同阶段重跑）

elif cur == "Executing":
    gap = self.completion_check(task) if self.completion_check else None
    if gap:
        task.retries += 1
        if task.retries > self.config.max_retries:
            task.blocked_reason = f"完成条件未满足：{gap}"
            task._set("Blocked", "completion_check")
        else:
            self._gap[task.id] = gap      # 下一轮 ctx 里明确告诉它缺什么
        return
```

应用侧（`review.py`）注册的条件：**每个待审文件都必须有结论**。

配套三件套（`findings.py`）：

| 机制 | 作用 |
|---|---|
| `ReviewSession.clean_claims` | 清白声明：文件看过、判定没问题 |
| `declare_clean(file, reason)` 工具 | 登记清白，要求已 `read_file` + 理由 ≥10 字，否则驳回 |
| `unaccounted()` | 既无有效 finding、也无清白声明的文件 = 覆盖缺口 |
| `review_status()` 工具（给 critic） | 审核前先查覆盖，有缺口直接打回 |

注意 `unaccounted()` 只认**形式审通过**的 finding：被驳回的条目不算"有结论"，该文件仍要重新给说法。

**验证**：同一组多文件复跑 —— 2 条有效发现 + 1 清白声明，打回 2 次后 `Done`。发现的那条是：

> `flask_sessions.py:368` — `Vary: Cookie` 只在"会话非空"分支加，空会话分支先 return 了，logout 清空 session 时响应会 `delete_cookie` 却不带 `Vary: Cookie`，中间缓存可能把用户相关响应发给别人。

这条是**真实的历史缺陷**（Flask 2.x 已按同样思路修掉）。不是"看着像问题"，是可验证的真问题。

### P1-1：同一处缺陷跨行报两次（**未修，已知限制**）

`requests/hooks.py` 里 `hooks = hooks or {}`（L24）和 `hooks = hooks.get(key)`（L25）是同一个"变量语义漂移"问题，因去重键是"文件+行"而报了两条。当前靠 critic 抽查推翻其中一条（本次确实推翻了，理由准确）。**根治需要"证据文本重叠度"或 AST 级归并，留到 P14。**

### P1-2：`python examples/codedoc/codedoc.py` 根本跑不起来

文档写着这么跑，实际 `ModuleNotFoundError: No module named 'statecraft'`——`codedoc.py` 少了 `sys.path` 引导（`review.py` 有）。已补 3 行。

### P1-3：注释生成的验收是假绿

原来判断"好注释已生效"用的是 `'"""按会员等级' in after`——**比对脚本预设的那句文案**。真实模型写的 docstring 永远不等于预设文本，这个断言在 `--live` 下必然假绿（真实模型跑完打印"好注释已生效: True"，但那是巧合/空真）。

改成 ast 计数：

```python
def _doc_stats(text):
    funcs = [n for n in ast.walk(ast.parse(text))
             if isinstance(n, (ast.FunctionDef, ast.AsyncFunctionDef))]
    return sum(1 for f in funcs if ast.get_docstring(f)), len(funcs)

docstring 覆盖率: 0/3 → 3/3
```

**换口径立刻抓出另一个问题**（P2-1）：离线剧本只补了 2 个函数，覆盖率 `2/3`，而 demo 文案一直说"三个函数"。补齐剧本后 3/3。

### P2-1 / P2-2：小问题

- 审非 `target.py` 的文件时，统计打印"干净文件误报: 15 条（期望 0）"——没有标准答案 ≠ 干净。改成"无标准答案文件：报了 N 条（需人工复核，不能直接算误报）"。
- 新写的覆盖闸门测试一开始继承 `unittest.TestCase`，两个 `async def` 用例被静默跳过（`coroutine never awaited`）。改成 `IsolatedAsyncioTestCase` 才真跑。**这类"测试假绿"比 bug 更值得警惕**——它会让"149 全绿"变成谎话。

## 五、这套东西到底"能用"到什么程度

**能用**：
- 状态机、打回、补偿、事件、看板、检索、评估——都真跑通了，不是 PPT。
- 审查器能报出**官方库里的真实历史缺陷**（`appnd_const` 文档笔误、`Vary: Cookie` 漏加），并且证据可逐字符核对。
- 幻觉检测是**确定性的**：证据对不上源文件就驳回（本次 1 条 `placeholder` 被抓），不靠第二个 LLM 当裁判。

**还不能用**：
- **漏报无法度量**。本次只测了"能不能报出真问题"和"会不会编造"，没有标准答案的真实代码**漏了多少不知道**。要回答这个，得有带标注的仓库级测试集（路线图里 L1-Code 的位置）。
- **成本未优化**。428 行一次审查要几十秒到几分钟、多次工具调用；重跑机制会放大成本。P14 增量审查（只审 diff）才是生产形态。
- **单文件规模上限不明**。1000 行的 `werkzeug/wsgi.py` 还没试。
- **跨行重复未根治**（P1-1）。

**一句话**：作为"公司内部代码注释 + 审查的多 Agent 底座"，机制层已经立住了（内核零改动就能挂第二条业务线）；缺的是**基准集**（证明漏报率）和**增量审查**（把成本压到能上 CI）。这两件正是路线图的 P13/P14。

### 7.2 又抓到一个 P0（这次是异常路径）

额度耗尽的接口返回 **HTTP 429 / `code=42906`「您的额度已用完」**。旧代码：

```
urllib.error.HTTPError: HTTP Error 429
  ↑ 打穿 orchestrator.run()，任务既不 Done 也不 Blocked
```

后果比崩溃更隐蔽：`reviews` 里留下一个永远 `draft` 的批次 —— 第二天没人知道它是死是活。

修法分两层：

```python
# providers/base.py —— 错误要带「能不能重试」，不能只带状态码
class ProviderError(Exception):
    def __init__(self, message, *, status=None, retryable=False): ...

# providers/openai_compat.py —— 同样是 429，含义可能相反
#   429 + "rate limit"  → 可重试（等一分钟就好）
#   429 + "额度已用完"   → 不可重试（等到明天也不会好，白等 90 秒）
exhausted = any(k in detail.lower() for k in ("额度", "余额", "quota", "insufficient"))
retryable = status in {408, 409, 425, 429, 500, 502, 503, 504} and not exhausted
```

编排器侧：`ProviderError` 可重试则按 `retry_backoff` 重试，不可恢复或重试用尽则抛
`TaskStalled` → 走既有升级链 → `Blocked`。**没有新增状态、没有新增分支**，复用原来的
「停滞升级」机制。实测收敛时间 1.3 秒（旧行为：traceback + 无终态）。

### 7.3 诚实说明：这轮没能跑通「真实模型 + 落库」的成功路径

该 key 的额度在本轮耗尽（42906），所以端到端成功路径这次的证据是：

- **数据层**：30 个持久层用例（幂等 / 约束 / 外键 / 统计口径 / 索引重建 / 记忆落盘）
- **流程层**：`--mock` 跑完整流水线后落库，5 条 finding 的 evidence / audit / form_ok 都对
- **异常层**：真实接口 429 的真实响应，验证降级与终态落库

P11 已经用真实模型跑通过成功路径（Flask `Vary: Cookie`、click `appnd_const` 等真实缺陷），
落库只是把同样的 `Finding` 写进表——但「真实模型 + SQLite」这一组合本身，本轮确实没验到。
